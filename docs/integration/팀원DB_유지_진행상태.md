# 팀원 DB 유지 방향 — 2026-11-06

기존 DB가 기준이다. 기존 컬럼 이름·기본키를 변경하는 과거 검토안은 사용하지 않는다.

## 코드 반영 완료

- `backend/app/db/models/user.py`: API의 `name`을 DB의 `display_name`에 연결.
- `backend/app/db/models/user_profile.py`: 기본키는 `user_id`. API의 `id`는 같은 값의 호환용 식별자로 반환하며 별도 DB 컬럼을 만들지 않는다.
- API의 `preferred_style`, `preferred_fit`은 DB의 `style_preference`, `fit_preference`에 연결.
- 기존 `favorite_color`, `updated_at`은 삭제하거나 수정하지 않는다.
- 관련 인증·프로필·인바디·피팅·스키마 점검 테스트 89개 통과. SQLite 테스트이며 실제 TiDB 저장 검증은 아니다.

## DB 추가 적용 완료 — 2026-11-06

- 실제 TiDB의 프로필에 `height_cm_precise DECIMAL(5,2)`, `weight_kg DECIMAL(5,2)`, `personal_color VARCHAR(80)`, `preferred_colors JSON`을 nullable로 추가했다. 기존 행의 새 컬럼은 NULL이며 가짜 프로필값을 채우지 않았다.
- 기존 ORM 정의에 따라 `inbody_records`를 추가했다. 회원 외래키를 포함하며 기록 데이터는 생성하지 않았다.
- 기존 `height_cm SMALLINT`와 `user_id` 기본키는 유지됐다. 기존 컬럼·행의 갱신, 이름 변경, 삭제는 하지 않았다.
- API 키 입력은 소수점 원본을 `height_cm_precise`에, 정수 호환값을 `height_cm`에 반올림하여 함께 저장한다. 예: 175.75 → 정확값 175.75 / 호환값 176. 기존 정수 데이터는 그대로 읽는다. 다른 프로그램이 정수 키를 다른 값으로 수정하면 그 값을 우선하여 오래된 정확값을 노출하지 않는다. 같은 반올림 구간 안의 외부 수정 의도는 구별할 수 없으므로 모든 프로필 쓰기 경로에서 두 컬럼을 함께 관리해야 한다.
- 신규 도구 `backend/app/db/profile_extension.py`: 기본 실행은 미리보기이며 `--apply`에서만 추가 DDL을 실행한다. 기존 구조가 예상과 다르면 중단한다. DDL 자동 커밋 때문에 실패 시 이미 추가된 항목이 남을 수 있고, 재실행 시 존재하는 호환 항목을 건너뛴다.
- 실행 결과: DDL 5개 완료, 남은 추가 작업 0개. 실제 DB 재조회에서 회원·프로필·인바디 ORM의 누락 컬럼 0개 확인.
- 관련 테스트 89개 통과, 타입 비교 보완 후 마이그레이션 관련 테스트 4개 추가 실행 통과. 테스트는 SQLite 및 타입 단위 검증이며 실제 TiDB API 쓰기 검증은 다음 단계다.

- 프로필 생성·조회·부분 수정 성공. 키 175.75cm가 소수점 손실 없이 반환됨.

- 주의: 검증 시에만 DB 의존성을 외부 트랜잭션에 연결했다. API의 commit 호출은 실제 flush까지 실행하지만 최종 영구 커밋은 하지 않는다. 영구 저장·서버 재시작 후 재조회 검증과는 구분한다.
- 실행 중인 서버의 frontend(5173), backend /health(8000), /openapi.json은 HTTP 200. 프론트의 /api/auth/status 프록시는 최초 5초 제한에서 시간 초과했으나 재확인에서는 HTTP 200 / configured 응답. 지속적인 프록시 장애는 재현되지 않았다.

### 실행 중인 서버의 영구 저장·재로그인 확인 완료 — 2026-11-06

- `backend/app/db/http_api_check.py` 추가. `python -m app.db.http_api_check --run`으로 실행하며, 기본 실행은 쓰기를 하지 않는다.
- `http://127.0.0.1:5173/api`를 통해 실제 Vite 프록시 → 실행 중인 FastAPI → 실제 TiDB 경로를 검증했다. DB 의존성 대체와 롤백을 사용하지 않았다.
- 회원가입, 로그인·본인 조회, 프로필 커밋, 인바디 커밋, 새 로그인 후 프로필 조회, 새 로그인 후 인바디 조회, 저장된 인바디의 피팅 초기값 반영 등 7개 확인 통과.
- DB에는 `ONFIT synthetic integration check`라는 이름의 합성 검증 계정과 프로필·인바디 기록이 남는다. 실제 사용자의 건강정보가 아니다. 기존 회원은 건드리지 않았다.
- 재실행은 `Semiproject-front/.tmp/http-api-check-account.json`의 동일 검증 계정을 사용한다. 해당 파일에는 검증 계정 비밀번호가 있어 Git 제외 여부를 확인했고, 토큰은 저장하지 않는다. 이 파일을 공유하거나 커밋하지 않는다.
- 새 계정 생성 직후 로컬 상태 파일 쓰기가 실패하거나 인바디 커밋 후 상태 파일 저장이 실패하면 일부 테스트 행이 남을 수 있다. 이 도구는 삭제를 자동 수행하지 않는다.
- 이번 결과는 HTTP API의 실제 저장과 새 로그인 후 조회에 한정한다. 브라우저 화면 조작과 백엔드 프로세스 재시작 후 조회는 아직 미검증이다.

### 백엔드 재시작 후 검증 완료 — 2026-11-06

8000 포트와 실행 경로를 확인해 ONFIT uvicorn 프로세스 트리만 종료하고 동일한 환경으로 다시 시작했다. 새 서버 프로세스의 시작 완료 로그를 확인한 뒤 HTTP 검증 도구를 재실행했다. 기존 계정 로그인·본인 조회, 기존 프로필, 기존 인바디, 피팅 초기값 조회 4개가 모두 통과했다. 새 계정·기록 생성은 없었다. 따라서 위의 재시작 미검증 상태는 이번 확인으로 해소됐다. 검증 도구의 일반 출력은 도구 자체가 서버를 재시작하지 않는다는 범위 설명이므로, 재시작 증거는 이번 수동 프로세스 확인 및 서버 로그와 함께 판단한다.

남은 검증은 브라우저에서 로그인 → 프로필 → 인바디 → 피팅의 실제 사용자 동선 확인이다. 현재 전체 통합 완료 상태로 표시하지 않는다.

과거 `database/migrations/review_auth_profile_inbody_20261106.sql`의 rename/rekey 제안은 폐기된 방향이며 실행하면 안 된다. 읽기 전용 `schema_audit`는 과거 ERD와의 이름 차이를 표시하는 도구이므로, 그 차이가 DB 변경 지시를 의미하지 않는다.
