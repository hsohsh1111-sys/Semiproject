# 공동 TiDB 연결 준비 — 2026-11-06

**최신 결과:** 사용자 비밀번호 수정 후 DB 접속에 성공했다. 인증 오류는 해결됐으며 실제 9개 테이블과 확정 ERD의 차이를 확인했다. 아래 인증 실패 내용은 이전 기록이다. 현재 차이·조치 순서는 [DB 호환성 조치안](./DB_호환성_조치안.md)을 우선 참고한다. 실제 데이터/스키마 변경은 하지 않았다.

## 최신 접속 결과

사용자가 최상위 `.env`를 만든 뒤 재점검했다. 백엔드는 해당 위치를 읽지 않고 기존 빈 `backend/.env`를 읽고 있었다. 원본은 보존하고 비어 있지 않은 DB 항목과 유효한 인증 시크릿만 `backend/.env`에 반영했다. 원본 일부 줄에는 dotenv 형식 오류가 있지만 DB 항목은 파싱됐으며, 값은 로그에 남기지 않았다.

일반/확장 권한의 읽기 전용 접속 시도에서 모두 실패했고, 추가 진단에서 DB 서버의 **1045 인증 거부**를 확인했다. URL과 TiDB 개별 필드의 호스트/사용자명/비밀번호/DB 이름이 일치함도 값 노출 없이 확인했다. 따라서 단순 경로 누락이나 두 설정값 불일치가 아니라 계정·비밀번호·접속 권한을 DB 담당자와 확인해야 한다. 테이블 조회·데이터 변경은 하지 못했다. 실제 API 서버는 이 실패 설정을 적용하기 위해 별도 재시작하지 않았다.

확인할 항목: 팀에서 제공한 전체 TiDB 사용자명, 비밀번호 원문·유효성, 해당 계정의 접속 허용/상태, 사용하려는 클러스터가 맞는지. 임의 비밀번호 추측·변경·새 계정 생성은 하지 않는다. 접속정보를 수정한 뒤 같은 감사 명령으로 재점검한다.

아래 ‘현재 확인된 상태’는 설정 파일 생성 전의 기록이다.

## 현재 확인된 상태

- 통합 프로젝트와 팀원 폴더의 확인한 위치에는 실제 DB 접속 `.env`가 없었다. 현재 프로세스 설정에도 DB URL·TiDB 필드·유효한 인증 시크릿이 없었다.
- 따라서 실제 TiDB에 접속하거나 테이블·회원 데이터를 확인하지 않았다.
- 확정 ERD의 이름은 `users.name`이다. 현재 SQLAlchemy User가 이 계약과 일치한다. `display_name`을 쓰는 `database/schema.sql`은 기존 점검 보고서에서 확인한 예전 SQL 초안이므로 그대로 실행하면 안 된다.
- 로컬 `backend/.env`에 입력 틀과 무작위 32바이트 인증키를 생성했다. DB 항목은 비워 뒀다. 기존 파일이 있다면 덮어쓰지 않는 방식으로 생성했고 실제 키를 화면·문서에 출력하지 않았다. Git 무시 여부를 확인했다.

## 팀원에게 요청할 내용

다음 문장을 팀원에게 전달하면 된다. Codex가 직접 메시지를 보내지는 않았다.

> 통합 프로젝트에서 사용할 TiDB 호스트, 포트, 사용자명, 비밀번호, DB 이름을 알려주세요. 현재 users 테이블의 이름 컬럼이 name인지 display_name인지도 확인 부탁드립니다. 기존 데이터를 보존해야 하니 테이블 생성·컬럼 변경 SQL은 아직 실행하지 않겠습니다.

접속정보는 팀에서 사용하는 비공개 수단으로 받아 로컬 파일에 입력한다. 비밀번호·전체 연결 문자열·인증키를 공개 저장소나 채팅에 붙여 넣지 않는다. 사용자별 공유·접근 정책은 DB 담당자와 정한다.

## 입력할 파일

`Semiproject-front/backend/.env`를 연다. 기존 `SECRET_KEY`는 로컬에서 생성했으므로 그대로 둬도 된다. 빈 값만 채운다.

```dotenv
DATABASE_URL=
TIDB_HOST=팀원이_준_호스트
TIDB_PORT=팀원이_준_포트
TIDB_USERNAME=팀원이_준_사용자명
TIDB_PASSWORD="팀원이 준 비밀번호"
TIDB_DATABASE=팀원이_준_DB이름
```

위 문자열은 설명용이다. 실제 접속정보로 바꾸기 전에는 연결할 수 없다. 포트는 숫자다. 현재 입력 틀에는 4000이 들어 있지만 팀원이 준 값을 우선한다. 비밀번호에 따옴표 등 특수문자가 있으면 dotenv 형식에 맞게 기록한다. 팀원이 전체 DATABASE_URL을 주었다면 그 방식만 사용해도 되며 개별 항목으로 중복 구성하지 않아도 된다.

## 읽기 전용 점검

backend 터미널에서:

```powershell
.\.venv\Scripts\python.exe -B -m app.db.schema_audit
```

- `not_configured`: 접속정보가 아직 없다. DB에 접속하지 않는다.
- `connection_failed`: 네트워크·인증·TLS 등을 확인해야 한다. 오류 유형만 출력하고 비밀번호·호스트·접속 문자열은 출력하지 않는다.
- `differences_found`: 확정 ERD에서 필요한 테이블/컬럼이 없다. 자동으로 고치지 않는다.
- `required_names_match`: 필요한 테이블·컬럼 이름이 존재한다. 자료형·PK/FK·인덱스·실제 API 저장까지 검증했다는 뜻은 아니다.

이 도구는 DB의 테이블·컬럼 메타데이터만 조회한다. 회원 행이나 비밀번호 해시를 읽지 않고 CREATE/ALTER/DROP/INSERT/UPDATE/DELETE를 실행하지 않는다. 추가 테이블·컬럼을 발견해도 삭제 대상으로 취급하지 않는다. 이름이 다르면 팀원과 검토한 뒤 별도 변경안을 준비한다.

계약: `database/erd_contract.json`은 확정 ERD/기존 점검 보고서의 11개 테이블·컬럼 이름을 추출한 자료다. DDL이나 임의의 새 테이블 설계가 아니다.

## 다음 단계

1. 팀원에게 접속정보를 받아 입력한다.
2. 위 점검 명령으로 실제 스키마 차이를 확인한다.
3. `name`/`display_name` 등 차이가 있다면 DB 담당자와 수정 방향을 합의한다. 기존 데이터가 있는 DB에 초안 SQL을 바로 실행하지 않는다.
4. 승인된 테스트 DB/계정에서 회원·프로필·인바디 API의 실제 저장·조회를 검증한다.
5. `.env` 변경 후 백엔드를 재시작해야 한다. `Start-ONFIT.ps1`은 실행 중인 서버를 재사용하므로 다시 실행하는 것만으로 환경변수가 갱신되는 것은 아니다. 기존 서버 종료 방법이 불명확하면 프로세스를 일괄 종료하지 말고 ONFIT 백엔드 재시작을 요청한다.

이번 검증은 `test_schema_audit.py`, `test_auth.py` 25개 통과이며 전용 메모리 SQLite를 사용했다. 실제 TiDB 테스트는 아직 하지 않았다.
