# 회원·프로필·인바디 DB 변경 검토 — 2026-11-06

**상태: 검토안만 준비. 공동 DB에 적용하지 않았다.** 실제 접속·메타데이터 조회만 했다. 인바디 체형 추정이나 3D 모델 기능을 추가하는 작업은 아니다.

## 변경 이유와 범위

현재 회원 ORM은 확정 ERD의 users.name을 사용하지만 실제 DB는 display_name을 사용한다. 프로필은 user_id PK이고 필요한 컬럼이 없으며, 인바디 테이블도 없다. DB 연결 성공만으로 회원·프로필·인바디 API가 호환되지 않는다.

이번 안은 **3개 테이블만** 다룬다. 상품·가격·크롤링·favorites·sellers·옷장 관련 테이블이나 다른 팀원 데이터를 변경하는 안이 아니다. 전체 11개 테이블 정합성이 완료되는 것도 아니다.

검토 SQL: [review_auth_profile_inbody_20261106.sql](../../database/migrations/review_auth_profile_inbody_20261106.sql). 파일은 **전체가 주석**이라 그대로 실행해도 SQL이 실행되지 않는다. 앱 시작 코드·자동 마이그레이션에는 연결하지 않았다.

| 대상 | 제안 | 주의할 영향 |
| --- | --- | --- |
| users | display_name을 name으로 전환 | 현재 팀원의 기존 인증 SQL이 깨질 수 있어 코드·DB 동시 전환 필요 |
| user_profiles | 새 이행 테이블에 복사·검증 후 원래 이름으로 교체 | id PK 생성, user_id UNIQUE/FK 유지. 기존 테이블은 별도 보존 |
| inbody_records | 현재 ORM과 같은 컬럼으로 생성 | 단위·시간대·자료형·FK 정책 검토 필요. 기존 기록을 임의 생성하지 않음 |

프로필 매핑은 height_cm/body_shape 유지, fit_preference→preferred_fit, style_preference→preferred_style, favorite_color→한 원소의 preferred_colors JSON 배열이다. 체중·퍼스널컬러는 알 수 없으므로 NULL이다. 기존 free-text가 현재 API 검증에 맞는지도 확인해야 한다. 이름을 바꿨다고 모든 값의 의미가 자동 검증되는 것은 아니다.

## 왜 프로필을 바로 ALTER하지 않는가

서버 버전은 읽기 전용 조회로 `8.0.11-TiDB-v8.5.3-serverless`를 확인했다. TiDB는 clustered PK 변경에 제한이 있어 기존 PK를 무조건 교체하는 SQL을 준비하지 않았다. 새 구조로 복사하는 방식도 테스트 DB에서 검증해야 한다. [TiDB clustered index 문서](https://docs.pingcap.com/tidb/stable/clustered-indexes/).

현재 메타데이터에서 다른 테이블→user_profiles의 FK는 없었다. 적용 직전 다시 확인해야 하며, 뷰·트리거·애플리케이션의 직접 SQL 의존성까지 없다고 검증한 것은 아니다. 테이블 교체 문법은 [TiDB RENAME TABLE 문서](https://docs.pingcap.com/tidb/stable/sql-statement-rename-table/)를 참고했다. 실제 서버에서 DDL을 실행해 검증하지 않았다.

이행/보존용 `user_profiles__...` 이름은 검토용 임시 이름이며 최종 애플리케이션 테이블 이름은 확정 ERD의 user_profiles를 유지한다. 기존 updated_at 등은 보존용 원본 테이블에 남긴다. 자동 삭제하지 않는다.

## 실제 적용 전에 필요한 확인

1. 공동 DB 담당자와 **현재 DB를 바꿔도 되는지**, 기존 팀원 서버의 동시 중단·코드 전환이 가능한지 확정한다. 어렵다면 별도 통합 테스트 DB에서 먼저 검증한다.
2. 복원 가능한 백업을 확보하고 복구 가능 여부를 확인한다. SQL 초안을 백업 대신 사용하지 않는다.
3. 검증하는 동안 회원·프로필·인바디에 쓰는 모든 서버·작업을 중단한다. 복사 중 쓰기를 허용하는 무중단 이행 안은 이번 범위에 없다.
4. 누락 FK·고아 프로필·height 범위·이행 이름 충돌·실제 charset/collation을 확인한다. 현재는 회원 행과 실제 프로필 값을 읽지 않아 통과 여부를 모른다.
5. 격리된 테스트 환경에서 복사 전후 건수와 필드별 일치를 검증하고, 테스트 계정으로 가입→로그인→프로필→인바디→피팅을 확인한다. 실제 개인정보를 테스트 fixture나 Git에 넣지 않는다.
6. 승인 후에만 단계별로 적용한다. 실패하면 완료된 단계만 기준으로 복구한다. DDL 전체가 한 번의 트랜잭션으로 되돌아간다고 가정하지 않는다.

## 되돌리기 조건

업무 쓰기를 재개하기 전에는 완료된 단계에 맞춰 보존한 프로필 테이블과 이전 회원 컬럼 이름으로 되돌리는 안을 검토할 수 있다. 신형 테이블은 지우지 않고 별도로 남긴다.

**새로운 가입·프로필 변경·인바디 기록이 생긴 뒤에는 단순 이름 되돌리기로 복구하면 안 된다.** 새 데이터·새 필드를 먼저 보존하고 역매핑·재동기화 계획을 별도로 검토해야 한다. 롤백 SQL은 모든 단계가 성공했다고 가정해 일괄 실행하는 용도가 아니다.

## 이번 확인 범위

- 실제 서버 버전·user_profiles로 들어오는 FK 메타데이터만 추가 조회했다. 현재 inbound FK는 0개다.
- SQL 파일 전체가 주석인지 로컬 확인했다.
- 실제 DDL·복사 INSERT·행 검증·API 저장·롤백은 **실행하지 않았다**. 그러므로 SQL 실행 성공이나 데이터 이행 성공으로 보고하지 않는다.
- Alembic은 README만 있는 상태라 검증되지 않은 자동 revision을 앱 시작에 추가하지 않았다. 공동 변경안 승인·테스트 후 버전 관리 방식도 확정해야 한다.
- 커밋·푸시·main 병합·배포는 하지 않았다.
