# 회원가입 이메일 인증 및 관리자 설정

## 최신 성능 보정 — 가입과 자동 로그인 통합

- 새 프론트는 POST /api/auth/signup-session을 한 번 호출해 UserPublic과 토큰을 함께 받는다. 기존 signup/login/me는 호환용으로 유지한다. 관리자/회원 통합 로그인과 세션 복원은 그대로다.
- 프론트 3회 요청을 1회로 줄이고 성공 후 900ms 지연을 제거했다. 가입 직후 login의 비밀번호 재검증도 피한다. 비밀번호 해시 강도·필수 동의·중복 방지·관리자 예약 검사는 유지한다.
- 매 요청의 users 스키마 검사와 정상 가입의 사전 중복 SELECT를 제거했다. DB UNIQUE 제약으로 원자적 중복 방지를 하고, INSERT 실패 시 rollback 후 중복 종류를 확인해 409로 안내한다.
- 앞선 ‘스키마 미적용 환경은 명확한 503’ 설명은 이 변경으로 대체된다. 필요한 DB 마이그레이션은 배포 전 전제 조건이며 이번 공동 DB에는 이미 적용됐다. 다른 환경에는 SQL 적용 여부를 확인해야 한다.
- 읽기 전용 TiDB 검사에서 SELECT1 39.3ms, 스키마 검사55.7ms 관찰. SQLite 합성 가입/자동 로그인 흐름은 SQL7회/157.2ms → SQL2회/75.1ms(각 1회 측정)였다. 네트워크·브라우저·Render 실성능 비교나 사용자 체감 개선율을 의미하지 않는다.
- 관련 백엔드44개·프론트14개·코드 빌드·가상 API 가입 UI 검사 통과. 운영 DB에 성능 측정용 계정은 생성하지 않았다. 커밋·푸시·배포 미실시.

## 최신 정책 — 연락용 휴대폰 번호 가입 (2026-11-12)

아래 이메일 인증 관련 기록은 이전 구현이다. 현재 회원가입 UI는 **아이디 → 닉네임/별명 → 연락용 휴대폰 번호 → 비밀번호 → 확인**이며 이메일·인증번호·발송 버튼을 제거했다. 휴대폰은 실제 소유 확인 없이 연락용으로만 저장하며, 로그인·비밀번호 복구·본인인증 수단으로 사용하지 않는다. 문자 발송 서비스는 연결하지 않았고 이번 작업에서 SMS를 보내지 않았다.

- SignupInput은 phone_number, phone_collection_consent, sms_marketing_consent를 받는다. 이메일 없는 신규 가입은 아이디와 연락처 수집 동의가 필수다. 이벤트 문자 동의는 선택이며 기본 false, 비동의여도 가입 가능하다.
- 휴대폰은 국내 형식만 검사하고 하이픈·공백을 제거해 저장한다. 실제 사용 여부는 확인하지 않는다. 전화번호를 계정 고유값으로 사용하지 않아 여러 계정이 같은 연락처를 등록할 수 있다.
- 기존 이메일 회원과 이메일 로그인은 유지한다. 기존 이메일 전용 API 계약의 인증 증명은 호환을 위해 남겼지만 새 UI는 사용하지 않는다. 가짜 이메일은 생성하지 않는다. 회원 공개 응답은 휴대폰 번호를 반환하지 않으며 관리자 가입 현황에는 마스킹 연락처와 이벤트 동의 여부만 표시한다.
- 사용자 승인 후 실제 TiDB users.email을 nullable로 변경하고 phone_number(nullable), sms_marketing_consent(default false), sms_marketing_consented_at(nullable)을 추가했다. 기존 회원 수와 기존 이메일이 있는 회원 수가 변경되지 않았음을 확인했다. 동의 시각은 서버 UTC 기준으로 저장한다.
- 변경 SQL: database/migrations/20261112_phone_contact_signup.sql. 다른 DB에는 적용 여부를 확인하고 필요한 문장만 실행한다. 데이터 삭제·관리자 자격증명 변경은 하지 않았다.
- 관련 백엔드 47개, 프론트 인증/세션 14개와 코드 빌드(write:false) 통과. 가상 API 브라우저 검사로 휴대폰 가입·수집 필수 동의·이벤트 선택 동의 기본 해제·가입 후 아이디 로그인·모바일 레이아웃을 확인했다. 실제 신규 회원을 공동 DB에 만들지는 않았다.
- 향후 이벤트 발송을 구현할 때는 해당 동의와 발송 중지 처리를 연결해야 한다. 현재 수신 동의 저장은 발송 완료를 의미하지 않는다. 커밋·푸시·운영 배포는 수행하지 않았다.

## 2026-11-12 변경

### 단일 회원가입 화면과 별도 아이디 (최신)

- 단계 탭을 없애고 사용할 아이디 → 닉네임/별명 → 이메일 인증·인증번호 → 비밀번호 → 비밀번호 확인 순서의 한 폼으로 정리했다.
- 로그인 아이디는 영문·숫자·점·밑줄·하이픈 4~32자이며 소문자로 정규화한다. 닉네임은 기존 display_name에 저장하고 헤더에 표시한다. 이메일은 인증·연락용으로 별도 보관하며 기존 이메일 로그인도 유지한다.
- SignupInput에 username을 추가했다. 이전 API 클라이언트와의 호환을 위해 선택 필드지만 새 회원가입 UI는 필수 입력이다. 아이디·이메일 각각 중복 가입을 거부하고 관리자 ID는 일반 가입에서 예약한다.
- 사용자 승인 후 공동 TiDB users에 `username VARCHAR(32) NULL`과 `uq_users_username` unique 인덱스를 실제 추가했다. 기존 회원 수가 유지됨을 확인했고 기존 회원의 username은 NULL이므로 이메일 로그인이 유지된다.
- migration 파일: `database/migrations/20261112_add_user_username.sql`. TiDB는 같은 ALTER에서 새 컬럼과 그 인덱스 추가를 거부(1072)해 컬럼 추가와 인덱스 추가를 두 문장으로 분리했다. 이미 반영한 DB에는 그대로 재실행하지 않는다. 다른 DB 환경은 스키마 확인 후 적용한다.
- 사용자 모델의 username은 지연 로딩으로 매핑해 마이그레이션 전 기존 회원 조회를 보호한다. 아이디 컬럼이 없는 환경의 신규 가입·아이디 로그인은 명확한 503으로 안내한다.
- 관련 백엔드 44개, 프론트 인증/세션 13개, 코드 빌드 통과. 단일 가입 폼·아이디/닉네임 전송·이메일 인증·닉네임 표시·390px 배치는 가상 API 브라우저 검사로 확인했다. 실제 발송 서비스 미연결로 실메일 인증·신규 실회원 가입은 미검증이다.

- 회원가입: 이름/닉네임, 이메일 인증번호 발송·확인, 비밀번호 확인 및 단계 표시.
- 가입 API는 `verification_token`이 없거나 이메일·목적·서명·만료가 맞지 않으면 403으로 거부한다. 기존 로그인 API와 기존 가입 계정은 유지한다. 신규 가입 클라이언트는 인증 후 받은 토큰을 보내야 한다.
- 새 API: `POST /api/auth/email-verification/request` (`email`), `POST /api/auth/email-verification/confirm` (`email`, `challenge_id`, `code`). Swagger `/docs`에 표시한다.
- 인증번호 6자리·5분 유효, 이메일과 접속 IP별 1분 재요청 제한·15분 5회, 오입력 최대 5회. 응답과 로그에 코드를 넣지 않는다. 성공 확인 후 같은 코드는 재사용 불가. 가입용 증명 토큰은 15분 유효하며 해당 이메일로만 가입 가능하다. 중복 계정은 기존 DB unique 제약과 중복 검사로 방지한다.
- 기존 인증된 회원 응답에 `is_admin`을 추가했다. 화면의 관리자 여부는 참고 표시이며, 가입 현황 API가 서버에서 매 요청 권한을 확인한다.
- 공개 관리자 메뉴·로그인 창 데모 링크 제거. 로그인 이름 옆에 로그아웃 표시. 관리자는 로그인 후 헤더에 별도 관리자 링크 표시. 일반 회원은 `#/admin`으로 직접 들어가도 차단된다.

## 실제 환경변수 설정

실제 값은 **backend/.env**와 Render 백엔드의 환경변수에만 넣는다. 프론트 VITE 변수나 Git에는 넣지 않는다.

### 관리자

이메일 관리자 지정 방식은 별도 ID 로그인으로 대체했다. `ADMIN_EMAILS`는 더 이상 사용하지 않는다. 일반 회원은 이메일이 같더라도 관리자 권한을 얻지 않는다.

프로젝트 최상위에서 다음을 실행하고 관리자 ID(기본 `onfit-admin`)와 비밀번호(8~32자)를 직접 입력한다. 사용자 요청으로 비밀번호와 확인 입력은 터미널에 표시되며, 저장은 해시만 backend/.env에 남긴다. 다른 기존 환경변수는 유지한다.

```powershell
.\Semiproject-front\backend\.venv\Scripts\python.exe .\Semiproject-front\backend\scripts\configure_admin.py
```

- `ADMIN_USERNAME`: 관리자 ID
- `ADMIN_PASSWORD_HASH`: 도구가 만든 Argon2 해시. 비밀번호 원문이 아니며 프론트에 노출하지 않는다.
- `SECRET_KEY`: 기존 인증 설정과 동일하게 충분히 긴 실제 서버 비밀키 필요.

Render 백엔드 Environment와 EC2 백엔드 환경파일에도 위 두 ADMIN 값을 복사하고 서버를 재시작한다. `$`가 포함된 해시를 셸에서 설정할 경우 작은따옴표로 감싸 셸 확장을 방지한다. 저장소에 .env나 실제 해시를 커밋하지 않는다. DB 관리자 사용자는 만들지 않으며 DB 스키마 변경도 없다.

**로그인 창은 회원·관리자 공통으로 하나만 사용한다.** 이메일 또는 ID 칸에 관리자 ID와 비밀번호를 입력하면 서버의 `/api/auth/login`이 관리자 설정과 비교해 인증하고 `auth_type=admin`을 반환한다. 프론트는 `/api/auth/admin/me`로 관리자 세션을 확인한 후 관리자 대시보드로 이동한다. 별도 관리자 로그인 창·링크는 제거했다. 기존 `/api/auth/admin/login` API는 호환을 위해 유지하지만 화면에서 사용하지 않는다. 관리자 ID는 신규 일반 회원 가입에서 예약 처리하며, 비밀번호 오류 시 회원 로그인으로 우회하지 않는다. 일반 회원과 토큰 목적은 여전히 분리되어 서로 대체할 수 없다. 관리자에게 개인 회원의 체형·인바디·옷장 세션을 부여하지 않는다.

관리자 설정이 비어 있으면 로그인은 503으로 차단한다. 초기 공통 비밀번호나 자동 우회 계정은 없다. 설정 ID/해시/SECRET_KEY가 변경되면 이전 관리자 토큰은 무효화된다. 로그인 시도는 IP별 15분 10회로 제한하며 단일 프로세스 기준이다. 다중 인스턴스에서는 공유 제한 저장소가 필요하다. 이메일 복구 기능은 없으며 비밀번호 변경은 같은 설정 도구로 수행한다.

별도 관리자 로그인·세션 복원·로그아웃 브라우저 가상 API 검사 통과. 관리자 API 및 설정 도구 테스트 5개 통과, 관련 인증·회원 회귀 검사는 별도 실행에서 통과했다. 실제 관리자 비밀번호는 아직 사용자가 입력하지 않아 실제 계정 활성화·Render/EC2 배포 검증은 미완료다.

### 로컬 SMTP

`EMAIL_PROVIDER=smtp`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_EMAIL`, `SMTP_USE_SSL` 설정. 465는 SSL true, 587은 false로 STARTTLS 사용. 계정 제공자가 요구하면 일반 비밀번호 대신 앱 비밀번호 사용. 이 문서에는 실제 자격증명을 기록하지 않는다.

### Render 무료 서버

Render Free는 SMTP 포트 25/465/587의 외부 연결을 차단한다. 배포에서는 HTTPS 발송 어댑터를 사용한다.

- `EMAIL_PROVIDER=brevo`
- `BREVO_API_KEY`: 발송 권한이 있는 API 키
- `BREVO_SENDER_EMAIL`: 해당 서비스에서 인증된 발신자 주소

계정·발신자 인증·발송 한도는 제공자에서 확인한다. 이번 작업은 계정 생성·유료 결제·실제 외부 발송을 수행하지 않았다. 키 미설정·제공자 거부·네트워크 오류는 503을 반환하며 인증을 우회하지 않는다. 제공자 수락과 실제 메일함 도착은 다르므로 실제 수신까지 확인해야 한다.

설정 후 로컬 백엔드를 재시작한다. `.env` 변경은 uvicorn의 Python 파일 자동 재시작 대상이 아닐 수 있다. 기존 Start-ONFIT.ps1 터미널을 Ctrl+C로 종료하고 다시 실행한다.

## 상태 저장 제약

인증번호·재발송 제한은 잠금으로 보호한 프로세스 메모리에 저장한다. **단일 서버·단일 worker 기준**이다. 재시작 시 진행 중 인증은 무효화되어 다시 발송해야 한다. 여러 worker/인스턴스로 늘릴 때는 공유 저장소로 이전해야 하며, 현재 구조를 분산 운영에 적합하다고 보장하지 않는다. 기존 TiDB 테이블·스키마는 변경하지 않았다.

## 검증과 남은 일

- 백엔드 97개, 프론트 인증·세션·찜 14개 통과. 실제 메일을 보내지 않는 테스트 사용.
- 프론트 코드 빌드(write:false, publicDir:false) 성공. 이번 변경 후 GLB 재복사를 포함한 전체 빌드는 반복하지 않았다.
- headless Chrome 가상 API 응답으로 가입 인증 단계·비밀번호 불일치·성공·이름·로그아웃·관리자 라우트·새로고침·390px 화면 확인.
- 실제 발송 계정과 관리자 이메일은 미설정. 실제 받은편지함 도착, TiDB 신규 가입, 운영 배포는 미검증. 커밋·푸시·배포 미실시.
