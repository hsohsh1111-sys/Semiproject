# 송성근 ONFIT 개발 작업일지

## 서버 실행 방법 — Windows / VS Code (2026-11-05 안내 수정)

> **고정 안내 · 2026-11-12 확인:** 개발할 때는 **http://127.0.0.1:5173/#/fitting** 을 사용한다. 주소만 열어서는 서버가 켜지지 않는다. PC를 재시작했거나 서버를 종료했다면 아래 통합 실행 명령을 다시 실행한다. 이미 서버가 실행 중이면 브라우저로 접속하면 된다.
>
> 통합 스크립트가 프론트엔드·백엔드·AI 패션 서버를 함께 실행한다. 실행한 터미널은 열어 두고, 종료할 때 `Ctrl+C`를 누른다. `4177`은 빌드 화면만 확인했던 임시 정적 서버 주소이며 개발 작업에는 사용하지 않는다.

### 권장: 프론트엔드·백엔드 한 번에 실행 (2026-11-06 추가)

프로젝트 최상위 `semiProject`에 `Start-ONFIT.ps1`을 추가했다. VS Code 터미널을 하나 열고 아래를 실행한다.

```powershell
Set-Location -LiteralPath 'E:\송성근(심화)\semiProject'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-ONFIT.ps1
```

- 꺼진 프론트엔드(5173)와 백엔드(8000)를 실행하고 HTTP 응답을 확인한다. 팀원 통합 후에는 AI 검색 개발 서버(5174)도 함께 실행한다.
- 이미 ONFIT이 실행 중이면 재사용하며, 다른 프로그램이 포트를 차지하면 중단하고 안내한다.
- 새 서버를 켰다면 이 터미널을 열어 둔다. `Ctrl+C`는 이 스크립트가 새로 시작한 서버만 종료한다. 기존에 별도 실행한 서버는 해당 원래 터미널에서 종료해야 한다.
- 두 서버가 이미 실행 중이면 주소만 출력하고 종료한다. 정상 동작이다.
- 3D 화면: http://127.0.0.1:5173/#/fitting / API 문서: http://127.0.0.1:8000/docs
- 오류 로그: `Semiproject-front/.tmp/dev-servers/`. 의존성 최초 설치는 아래 개별 실행 안내를 참고한다.
- `ExecutionPolicy Bypass`는 이 PowerShell 실행에만 적용하며 PC의 정책을 영구 변경하지 않는다.

2026-11-06에는 두 서버가 실행 중인 상태에서 스크립트를 실행해 중복 실행 없이 재사용하고 종료하는 경로를 확인했다. 이 검증에서 기존 서버를 강제로 끄거나 콜드 스타트를 재검증하지 않았다. 아래는 개별 실행이 필요할 때의 기존 안내다.

**화면만 확인하려면 1번, 로그인·API 기능까지 사용하려면 1번과 2번을 모두 실행한다.** 터미널은 프론트엔드용과 백엔드용으로 각각 하나씩 사용한다. 아래 명령은 PowerShell 기준이며 각 코드 블록을 복사해 실행하면 된다. PC를 재시작하거나 서버를 종료하면 다시 실행해야 한다.

### 1. 프론트엔드 실행: 웹 화면 열기

VS Code 상단 메뉴 **터미널 → 새 터미널**을 누른다. 아래 두 줄을 실행한다. 절대 경로이므로 현재 터미널이 어느 폴더에 있어도 사용할 수 있다.

```powershell
Set-Location -LiteralPath 'E:\송성근(심화)\semiProject\Semiproject-front\frontend'
npm.cmd run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

터미널에 `VITE ... ready`와 `http://127.0.0.1:5173/`가 표시되면 프론트엔드가 시작된 것이다. **이 터미널은 실행 상태로 두고**, 브라우저에서 아래 주소를 연다.

| 확인할 화면 | 브라우저 주소 |
| --- | --- |
| 3D 피팅 | [http://127.0.0.1:5173/#/fitting](http://127.0.0.1:5173/#/fitting) |
| 홈 | [http://127.0.0.1:5173/#/home](http://127.0.0.1:5173/#/home) |

`index.html` 파일을 더블클릭하는 대신 위 주소로 접속한다. 피팅 화면에서 인체형 GLB와 원하는 의류를 선택해 확인한다. 화면이 열려도 로그인·서버 계산·상품 API 요청에는 백엔드가 필요할 수 있다.

### 2. 백엔드 실행: 로그인·피팅 API 사용

프론트엔드 터미널은 그대로 두고 **터미널 → 새 터미널**로 두 번째 터미널을 연다. 현재 프로젝트의 백엔드 `.venv` Python을 직접 실행하므로 가상환경 활성화 명령은 필요 없다.

```powershell
Set-Location -LiteralPath 'E:\송성근(심화)\semiProject\Semiproject-front\backend'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

`Uvicorn running on http://127.0.0.1:8000`와 `Application startup complete`가 나오면 시작된 것이다. 이 터미널도 실행 상태로 둔다.

| 확인할 항목 | 브라우저 주소 | 정상 확인 방법 |
| --- | --- | --- |
| 백엔드 실행 상태 | [http://127.0.0.1:8000/health](http://127.0.0.1:8000/health) | `status: ok` 응답 |
| Swagger API 문서 | [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs) | ONFIT API 문서 표시 |

기본 프론트엔드 API 주소는 `http://localhost:8000/api`다. `VITE_API_BASE_URL`을 별도로 설정했다면 해당 설정을 우선한다. `/health` 성공은 서버 실행 확인이며 TiDB 연결·인증 설정·AI 모델 연결까지 검증했다는 뜻은 아니다. 로그인·DB 기능에는 기존 환경변수 설정이 필요하다. 비밀번호나 연결 문자열을 작업일지에 붙여 넣지 않는다.

### 3. 자주 생기는 문제와 종료 방법

| 증상 | 확인·조치 |
| --- | --- |
| 브라우저에서 연결할 수 없음 | 해당 서버 터미널이 실행 중인지 확인한다. 종료됐다면 위 명령으로 다시 시작한다. |
| `Port 5173 is already in use` | 이미 프론트엔드가 실행 중일 수 있다. 먼저 피팅 주소를 연다. 재시작하려면 기존 서버 터미널에서 `Ctrl+C`를 누른 뒤 다시 실행한다. `--strictPort` 때문에 임의로 5174로 바뀌지 않는다. |
| 8000 포트 사용 중 오류 | 기존 백엔드 터미널을 확인한다. `/health`가 열리면 중복 실행할 필요가 없다. |
| `npm` 스크립트 실행 정책 오류 | 위 안내처럼 `npm.cmd`를 사용한다. |
| `package.json`을 찾을 수 없음 | 1번의 `Set-Location`부터 다시 실행한다. |
| `vite`를 찾을 수 없음 | frontend 폴더에서 최초 의존성 설치가 필요한지 확인하고 `npm.cmd install` 후 다시 실행한다. 매번 설치할 필요는 없다. |
| `.venv\Scripts\python.exe`를 찾을 수 없음 | backend 폴더가 맞는지 확인한다. 가상환경이 없는 PC에서만 아래 최초 설정을 진행한다. |
| API에 연결할 수 없음 | 백엔드 실행 여부와 `VITE_API_BASE_URL`을 확인한다. |
| 화면은 열리지만 3D 오류 안내가 나옴 | 서버 실행과 별개의 렌더링 오류일 수 있다. `F12 → Console`의 빨간 오류 내용을 확인한다. |

새 PC 등 **backend 가상환경이 없는 경우에만**, backend 폴더의 터미널에서 최초 설정한다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

설치가 끝나면 2번의 uvicorn 명령을 실행한다. `python` 자체를 찾지 못하면 팀에서 사용하는 Python 설치가 먼저 필요하다.

서버를 끄려면 **각 서버가 실행 중인 터미널을 선택하고 `Ctrl+C`**를 누른다. 다시 켤 때는 1번·2번 명령을 사용한다.

이번 수정은 실행 안내 문서만 정리한 것이며, 현재 서버 실행 여부나 브라우저 동작을 새로 검증한 기록은 아니다. 아래 개발 내역의 기존 날짜·검증 결과는 당시 기록을 유지한다.

이 문서는 송성근 담당 기능의 실제 작업 내역과 코드 위치를 찾기 위한 누적 작업일지다. 개발 전 상태와 계획은 [개발 시작 점검 보고서](./송성근_개발시작_점검.md)를 참고한다.

**최종 정리일: 2026-11-05, 한국 시간.** 기존 작업 001~021을 보존하고 이후 작업 022~029를 추가했다. 아래 과거 기록의 모델 버전·미완료 상태·테스트 결과는 당시 기준이다. 최신 상태는 바로 아래 요약과 작업 022~029를 우선 참고한다. 이번 일지 작성은 문서 수정만 진행했으며 테스트·빌드·서버·배포를 재실행하지 않았다. 직전 GitHub 커밋·푸시 결과는 작업 029에 별도로 기록했다.

## 2026-11-12 — 회원가입·이메일 인증·관리자 접근 개선

### 상단 돋보기 기능 검색

- 기존 스타일 추천으로 바로 이동하던 돋보기를 검색창으로 변경했다. 입력 중 연관 기능이 아래 표시되며 클릭 또는 Enter로 해당 페이지에 이동한다.
- 인바디·체형·의류는 3D 피팅, 이미지·사진은 AI 패션 검색, 찜은 옷장 등 기존 페이지와 검색어를 연결했다. 가격처럼 여러 결과가 있으면 목록을 제공한다. 관리자 결과는 관리자에게만 표시한다.
- 방향키 선택, Escape·바깥 클릭·닫기로 종료, 모바일 검색창을 지원한다. 일치하는 기능이 없으면 안내하며 임의 페이지로 이동하지 않는다. 입력 중 API 요청을 보내지 않는 기능 검색이며 실제 상품 자동완성은 아니다.
- 변경: Header.jsx, FeatureSearch.jsx/CSS, featureSearch.js 및 테스트. 검색 단위 테스트 4개 통과, 로컬 Chrome에서 데스크톱·모바일 목록/클릭/키보드 이동/결과 없음/닫기 확인(API Mock 사용). 자산 복사·파일 쓰기 없는 프로덕션 컴파일 성공. 커밋·푸시·배포는 하지 않았다.

### 마이페이지 및 회원탈퇴 추가

- 일반 회원으로 로그인하면 상단에 `마이페이지`가 표시된다. 아이디·닉네임·휴대폰 번호·이벤트 문자 동의 여부·가입일을 본인만 확인하고, 3D 피팅 및 옷장으로 이동할 수 있다.
- 회원탈퇴는 마이페이지 하단 `계정 관리`의 작은 링크로 배치했다. 클릭하면 삭제 안내, 현재 비밀번호, 최종 동의 및 취소 버튼이 표시된다. 메뉴에서 찾을 수 있도록 유지하면서 주요 기능보다 낮은 시각적 비중을 적용했다.
- `GET /api/auth/account`, `DELETE /api/auth/account` 추가. 탈퇴 시 본인 계정 및 연결된 프로필·인바디·코디·찜 정보를 한 트랜잭션으로 삭제한다. 다른 회원과 공용 상품은 유지한다. 알 수 없는 외래키 연결로 삭제가 막히면 전체 작업을 롤백한다.
- 탈퇴 성공 시 로그인 세션과 해당 회원의 로컬 피팅 치수를 정리한다. 삭제된 회원의 기존 토큰은 서버 조회에서 거절된다.
- 기존 관리자 가입 현황 화면은 일반 로그인창에서 설정된 관리자 계정으로 로그인한 경우에만 상단 `관리자` 메뉴로 연결된다. 일반 회원은 API에서도 접근할 수 없다. 환경설정 기반 관리자 계정은 일반 회원탈퇴 대상이 아니다.
- 검증: 격리된 SQLite에서 본인 조회·비밀번호 확인·본인 데이터 삭제·타인 데이터 보존·토큰 무효화·삭제 실패 롤백을 확인했다. 로컬 Chrome에서 Mock API로 마이페이지·취소·동의·오류·탈퇴 후 로그아웃 및 관리자 화면 전환을 확인했다. 실제 공동 TiDB 회원은 삭제하지 않았다. 프론트엔드 빌드는 자산 복사와 파일 쓰기를 제외한 프로덕션 컴파일로 확인했다.
- 확인 주소: `http://127.0.0.1:5173/#/mypage`. 아직 커밋·푸시·Render 재배포하지 않았다.

**회원가입 대기 개선:** 기존 프론트의 signup→login→me 3회 요청과 성공 후 900ms 고정 지연을 확인했다. `POST /api/auth/signup-session`을 추가해 가입 결과·토큰을 한 번에 반환하고 `auth.js`·`AuthModal.jsx`를 연결했다. 기존 signup/login/me 계약은 유지한다. service.py의 매 요청 스키마 조회와 정상 가입의 사전 중복 조회는 제거하고 DB unique 제약+실패 시 중복 확인으로 처리한다. 비밀번호 해시 설정은 약화하지 않았다. 실제 TiDB 읽기 전용 SELECT1 39.3ms·스키마 검사55.7ms를 관찰했고, SQLite 합성 흐름은 SQL 7회/157.2ms에서 2회/75.1ms로 바뀌었다(각 1회 측정, 운영 성능 보장 아님). 관련 백엔드44개·프론트14개·코드 빌드·가상 API 브라우저 검사 통과. 실제 신규 회원을 공동 DB에 만들지는 않았다.

**가입 전 약관 동의:** `SignupTerms.jsx`에서 전체 동의·만14세 이상 확인·이용약관·개인정보 필수 동의·이벤트 문자 선택 동의 및 보기/펼치기를 구현했다. 필수 동의가 완료돼야 가입 입력 화면으로 넘어가고 서버도 같은 필수 항목을 검사한다. `AuthModal.jsx`의 휴대폰 라벨을 ‘휴대폰 번호’로 바꾸고 설명은 삭제했다. 사용자 승인에 따라 실제 공동 TiDB users.signup_consent(JSON nullable)을 추가해 서버 약관 버전·UTC 동의 시각·항목별 선택 내역을 저장한다. 기존 회원에게 동의를 소급 생성하지 않았다. 관련 백엔드 41개·프론트 14개·코드 빌드·가상 API 모바일 브라우저 검사 통과. 약관 본문은 운영 정책 확정 전 초안이며 후속 개정/철회 이력 기능은 미구현이다. 상세: `Semiproject-front/docs/integration/가입약관_동의기록.md`.

**최신 변경 — 이메일 인증 보류·연락용 휴대폰 수집:** `AuthModal.jsx`에서 이메일/인증번호를 제거하고 휴대폰 번호·수집 필수 동의·이벤트 문자 선택 동의를 추가했다. `auth.js`는 이메일 없이 가입 후 선택한 아이디로 로그인한다. 백엔드 schemas/service/User 모델에 연락처·선택 동의·서버 동의시각을 저장하고, 관리자 API/페이지는 연락처를 마스킹해 표시한다. 실제 인증·문자 발송은 하지 않는다. 사용자 승인 후 공동 TiDB의 email nullable 변경과 phone_number·sms_marketing_consent·sms_marketing_consented_at 추가를 적용했으며 기존 회원/이메일 데이터 수량을 보존했다. SQL은 `database/migrations/20261112_phone_contact_signup.sql`. 관련 백엔드 47개·프론트 14개·코드 빌드 및 가상 API 모바일 가입 흐름 통과. 실제 신규 계정 생성·운영 배포·커밋·푸시는 미실시다.

**회원가입 한 화면 정리·로그인 아이디 분리:** 이메일 인증/계정 만들기 탭을 제거하고 아이디·닉네임/별명·이메일 인증·비밀번호·확인 순서로 변경했다. username은 소문자 정규화, 4~32자, 중복 불가이며 닉네임은 display_name과 헤더 표시를 유지한다. 사용자 승인 후 공동 TiDB users.username(nullable)과 unique 인덱스를 추가했고 기존 회원 수가 유지됐다. TiDB의 복합 ALTER 제한으로 실패한 첫 요청은 컬럼/인덱스 두 문장으로 분리해 정상 적용했다. 변경 SQL은 `Semiproject-front/database/migrations/20261112_add_user_username.sql`, 관련 코드는 `backend/app/db/models/user.py`, `features/auth/{schemas,service,router}.py`, `frontend/src/components/common/AuthModal.jsx`, `services/auth.js`. 백엔드 관련 44개·프론트 13개·코드 빌드·가상 응답 브라우저 검사 통과. 실제 이메일 발송은 여전히 미설정이다.

**이메일 발송 실패 안내 보정:** 발송 계정 미설정 상태가 재요청 제한에 먼저 반영되던 순서를 수정했다. 설정이 없으면 반복 요청도 명확한 503 안내를 반환하며 제한 횟수를 소비하지 않는다. 인증번호 입력란은 가입 화면에서 항상 보이고, 실제 발송 성공 전에는 비활성화한다. 제한 응답의 Retry-After도 화면 대기시간에 반영한다. 관련 백엔드 5개·프론트 5개와 코드 빌드, 미설정 상태의 가상 응답 브라우저 검사를 통과했다. 로컬 서버 재시작 완료. 실제 메일 발송 서비스는 아직 미연결이다.

**로그인 화면 통합:** 사용자 요청으로 별도 관리자 로그인 모드를 제거했다. 공통 로그인 창에서 서버가 관리자 ID를 판별해 관리자 인증을 수행한다. 관리자 성공 시 대시보드 이동, 회원은 기존 화면을 유지한다. 관리자 토큰·세션 권한 분리는 유지하며 관리자 ID로 일반 가입하거나 비밀번호 오류 후 회원 인증으로 우회하는 경로는 차단한다. 관련 백엔드 42개·프론트 인증/세션 13개와 코드 빌드 통과. 실제 비밀번호는 출력·변경하지 않았다.

**추가 변경 — 별도 관리자 ID 방식:** 실제 이메일 없이 관리자 ID·비밀번호로 로그인하도록 `backend/app/features/auth/admin_auth.py`와 `/api/auth/admin/login`, `/admin/me`를 추가했다. 서버의 `ADMIN_USERNAME`·`ADMIN_PASSWORD_HASH`로 관리하며 DB 계정/스키마는 만들지 않는다. `backend/scripts/configure_admin.py`로 비밀번호를 직접 입력해 해시만 저장한다. 이메일 관리자 지정 방식은 폐기했다. 프론트 `auth.js`, `authSession.js`, `AuthModal.jsx`, `App.jsx`, `Header.jsx`는 관리자 세션을 회원 세션과 분리한다. 기존 일반 회원 이메일 인증은 유지한다. 관리자 테스트 5개·프론트 관련 테스트 16개 통과, 별도 관리자 로그인·새로고침·로그아웃은 가상 API 브라우저 검사로 확인했다. 실제 관리자 설정·메일 발송·운영 배포는 미완료이며 자격증명을 임의로 만들지 않았다.

### 작업 026 — 마른·보통·근육형 체형과 키 조절 정리

- **목적:** 사용자가 모든 cm 수치를 알아야 하는 방식 대신 체형을 먼저 고르고 필요하면 세부 조절하게 한다. 인바디만으로 정확한 외형을 복원하기 어렵다는 점을 전제로 했다.
- **초기 접근의 한계:** 프리셋 치수만 바꾸면 몸의 크기만 달라 보였다. 이를 보완하기 위해 기존 MPFB 해부학적 타깃을 사용해 `body_build_lean`, `body_build_muscular`라는 실제 정점 변형을 추가했다.
- **제작 방법:** `frontend/scripts/create_body_builds.py`에서 원본 `ONFIT_Human_BodyMorph_v3.blend`의 정점 순서·기존 18개 키·기본 가중치를 유지하고 새 버전으로 내보냈다. 근육형은 상완·전완·어깨·등·허벅지·종아리 등의 국소 변형을 조합했다. JavaScript 도형으로 인체를 다시 만들지 않았다.
- **의류 대응:** `prepare_build_clothes.py`에서 인체의 체형 변위를 인접 의류 정점에 전달하고 변위장만 제한적으로 보간했다. 상의·하의·아우터는 공통 체형을 참조하되 의류별 착용 상태·재질은 독립적으로 유지했다. 원단 물리 시뮬레이션은 아니다.
- **키/체중:** 체중 입력 UI는 제거했지만 기존 API의 체중 필드는 내부적으로 유지했다. 키는 세로만 늘리던 방식에서 가로·세로·깊이를 같은 비율로 바꾸는 방식으로 수정했다. 발바닥은 바닥에 유지하고 의류도 같은 부모 좌표계에서 움직인다. 키만으로 실제 인체 비율을 추정하는 기능은 아니다.

- **핵심 파일:** `frontend/src/components/fitting/bodyPresets.js`, `bodyMorphs.js`, `glbGeometry.js`, `GlbMannequinModel.jsx`, `garmentGlb.js`, `glbCamera.js`, `frontend/src/pages/FittingPage.jsx`.

### 작업 027 — 근육형 과장 완화와 팔 두께 소폭 보정

- **발생 문제:** 근육을 강조하는 과정에서 가슴·복부가 과장되고 어깨·겨드랑이가 각지게 보였다. 복근 홈과 표면 음영을 강하게 넣을수록 인체가 더 부자연스러워진다는 사용자 피드백이 있었다.
- **기본 형상 보정:** 원본 체형에 포함된 가슴·복부 기여분을 별도 보정 키로 완화했다. 기존 기본 가중치를 무조건 0으로 지우지 않고 보정 키를 추가했다. 근육형의 겹친 변위는 어깨·겨드랑이에서만 제한적으로 부드럽게 연결했다.

- **현재 복근 강도:** `bodyMorphs.js`의 `MUSCULAR_ABS_WEIGHT=.25`. 기존 1에서 0.25로 낮춰 실루엣 중심으로 단순화했다. 가슴·복부·의류·피부를 발광 재질로 보이게 하는 처리는 하지 않았다.

- **생성 파일:** `assets/blender/ONFIT_Human_BodyBuild_v11.blend`, `frontend/public/models/ONFIT_Human_BodyBuild_v11.glb`, 같은 이름의 제작 JSON. 원본과 v10을 덮어쓰지 않았다. React의 인체 경로만 v11로 교체했다. 의류는 v10을 유지했다.
- **수정 코드:** `frontend/scripts/create_body_builds.py`, `frontend/src/components/fitting/bodyMorphs.js`, `bodyAppearance.js`, `GlbMannequinModel.jsx` 및 `bodyAppearance.test.js`, `bodyBuilds.test.js`.

### 작업 028 — 미사용 UI와 임시 빌드 폴더 정리

- **원인:** 검증할 때마다 `.codex-*` 출력 폴더를 새로 만들면서 모델 복사본과 로그가 누적됐다. 과거 결과 보존을 위한 방식이었지만 검증 후 정리를 하지 않아 폴더 수·용량이 불필요하게 늘었다.

## 2026-11-09 — Render 분리 배포 경험 및 면접·취업 준비 핵심 정리

### 실제 ONFIT에 적용한 배포 구조

| 서비스 | 역할 | 공개 주소 |
| --- | --- | --- |
| OnFit — Python Web Service | FastAPI 인증·DB 저장·피팅 계산 API | https://onfit-o49d.onrender.com |
| OnFit-web — Static Site | React 화면과 3D 모델 등 정적 파일 제공 | https://onfit-web.onrender.com |

사용자는 OnFit-web에 접속한다. 화면의 로그인·저장 요청은 OnFit API로 전달된다. 백엔드 기본 경로 `/`에는 홈페이지를 등록하지 않았으므로 Not Found가 나와도 서버 전체의 장애를 뜻하지 않는다. 백엔드 실행 상태는 `/health`로 확인한다.

프론트 빌드 환경의 VITE_API_BASE_URL로 API 주소를 지정하고, 백엔드 FRONTEND_ORIGINS에 실제 프론트 origin을 등록했다. 처음에는 프론트 origin에 대한 CORS 사전 요청이 400이었고, 설정 변경·재배포 후 HTTP 200과 올바른 Access-Control-Allow-Origin 응답을 확인했다. 무료 백엔드의 최초 요청은 시간 초과했지만 재확인에서는 /health가 정상 응답했다. 이를 모든 지연의 원인이 절전이라고 확정한 것은 아니다.

서비스 Live 및 공개 HTTP 응답 확인과 로그인·DB·3D의 배포 환경 전체 검증은 구분한다. EC2 실제 배포는 아직 수행하지 않았다.

### ★ 면접 핵심: 분리 배포를 선택한 이유와 한계를 설명하기

> **프론트엔드와 백엔드가 서로 영향을 주지 않는 변경은 각각 독립적으로 배포할 수 있다. 다만 API 계약이 바뀌는 기능은 배포 순서를 조율해야 한다.**

개발 담당자를 나누는 것과 배포 서비스를 나누는 것은 별개의 선택이다. 담당자가 달라도 하나의 서버에 함께 배포할 수 있고, 분리 배포도 반드시 서로 다른 물리 서버를 뜻하지 않는다. ONFIT에서는 Render의 정적 사이트 서비스와 Python API 서비스를 각각 사용했다. 이를 마이크로서비스 아키텍처를 구현한 경험이라고 과장하지 않는다.

| 진행 상황 | 프론트·백엔드 분리 배포 | 하나의 앱으로 묶어 배포 |

**하나의 서버에서는 반드시 상대 작업이 끝날 때까지 기다려야 한다는 뜻이 아니다.** 브랜치와 릴리스를 관리하면 서버 하나에서도 완성된 변경만 배포할 수 있다. 분리 배포는 배포 범위와 영향 대상을 나누기 쉽게 한다는 장점이 있다.

### 독립 배포에도 순서 조율이 필요한 예시

새로운 인바디 기록 삭제 기능을 추가할 때는 삭제 API가 먼저 준비되어야 삭제 버튼을 실제로 사용할 수 있다. 기존 기능과 호환되는 API를 먼저 배포·확인하고, 그 API를 사용하는 프론트를 배포할 수 있다. 기존 API의 필수 필드나 응답 형식을 깨는 변경이라면 호환 기간·버전 관리 등 추가 조율이 필요하다. 서버를 나눴다고 API 의존성이 사라지는 것은 아니다.

### 장점과 비용을 함께 설명하기

- 장점: 화면 수정과 API 수정을 별도로 배포하고, 문제 발생 시 수정·롤백 범위를 나누기 쉽다. API가 중단돼도 정적 화면 파일은 제공될 수 있다.
- 관리 비용: 두 서비스의 환경변수·주소·로그를 관리하고, origin이 다르면 CORS도 설정해야 한다. 화면이 뜬다고 로그인·저장이 정상이라는 뜻은 아니다.
- 단일 서버 대안: FastAPI가 React 빌드 파일까지 제공하면 같은 주소로 운영할 수 있다. 배포와 관리는 단순해질 수 있지만 앱 재시작이 화면 제공에도 영향을 줄 수 있다.
- 결론: 분리가 항상 더 빠르거나 저렴한 것은 아니다. ONFIT은 기존 구조와 팀 협업에 맞춰 분리 배포를 사용했으며, 프로젝트 규모·운영 방식에 따라 단일 배포도 유효하다.

### ★ 면접 답변 예시 — 본인이 한 일과 확인한 범위 중심

> ONFIT에서는 React 프론트를 Render Static Site에, FastAPI 백엔드를 별도 Web Service에 배포했습니다. 화면과 API를 각각 배포할 수 있도록 구성했으며, 프론트의 API 주소와 백엔드의 허용 origin을 연결했습니다. 처음에는 CORS 사전 요청이 실패했는데 실제 프론트 주소를 허용한 뒤 정상 응답을 확인했습니다. 분리 배포는 서로 독립적인 수정의 배포 범위를 줄이는 데 유리하지만, 새 API를 사용하는 화면은 배포 순서를 맞춰야 한다는 점도 배웠습니다.

이 답변은 실제 구성·CORS 조치 경험을 바탕으로 한다. 독립 배포로 개발 시간을 얼마나 단축했는지, 실제 사용자 규모나 무중단 운영을 달성했는지는 측정하지 않았으므로 성과로 주장하지 않는다.
